Registrar Desk API

Four endpoints cover the registrar's flow: find an application awaiting registration, review its full detail and fee readiness, and commit the registration to create the student record. A fifth is a static dropdown lookup.

/api/v1/admissions/registrar-desk

Response envelope

Every response — success or failure — is wrapped the same way. Read success first; on failure, loop errors regardless of which endpoint or validation rule produced it.

// 200 OK
{
  "success": true,
  "data": { /* payload — shape documented per endpoint below */ },
  "message": null,
  "code": null,
  "errors": null
}

// 400 / 404 — validation or business-rule failure
{
  "success": false,
  "data": null,
  "message": null,
  "code": "bad_request",  // or "not_found"
  "errors": [ "Please make sure that Registration Fee is Paid before proceeding." ]
}
Rule of thumb — show errors[0] (or all of them, for validation) to the user as-is; these are already human-readable registrar-facing messages, not codes to translate.

Application statuses

The queue is driven by one status byte on the application. The registrar desk only ever expects RegistrarVetted in the queue and only ever moves an application to Registered.

1
Received
Not yet vetted — never appears at this desk.
2
RegistrarVetted
Default queue filter. "Provisionally Admitted — Awaiting Final Registration."
3
RejectedByRegistrar
Not shown in this queue by default.
4
Registered
Set automatically once POST /register succeeds.
GET /applications GetRegistrarDeskApplications

01 · Find — the search queue. Filter and page through applicants awaiting registration. Omit status to get the default queue (RegistrarVetted).

Query parameters — all optional
ParamTypeNotes
appRefNostringExact match.
studentNamestringPartial match (contains).
emailstringExact match.
phonestringExact match.
programGuidguidFilter to one program.
intakeGuidguidFilter to one intake.
intakeNamestringAlternate to intakeGuid.

pageintDefault 1.
pageSizeintDefault 10.
 
"data": {
  "items": [
    {
      "applicationGuid": "3f2a...-guid",
      "appRefNo": "APP-2026-0142",
      "studentName": "Amina Yusuf",
      "programName": "BSc Computer Science",
      "intakeName": "Jan 2026",
      "regPaid": true
    }
  ],
  "totalCount": 47,
  "pageNumber": 1,
  "pageSize": 10
}
regPaid gates the Register button — true means the registration fee is fully paid for this application; show the Register action as enabled. false means an outstanding balance remains; disable/hide the button for that row (the registrar should send the applicant back to Payment Console first). The POST /register endpoint independently re-checks this server-side, so the client-side gate is a UX convenience, not the source of truth.
GET /applications/counts GetRegistrarDeskCounts

Summary tile counts for the queue header — no parameters. Independent of whatever filters are currently applied to the search grid.

"data": {
  "regFeePaidCount": 31,      // vetted apps where regPaid = true
  "regFeeNotPaidCount": 16,   // vetted apps where regPaid = false
  "registeredCount": 212     // already registered, current intake
}

POST /applications/{applicationGuid}/register RegisterStudent

03 · Commit — creates the student record and returns login credentials. Call this only when regPaid / registrationFeeConfirmed is true; the server re-validates and will reject the call otherwise.

Known server-side rejections (all returned as errors[0], HTTP 400)
MessageCause
"Only vetted applications can be registered."Application status isn't RegistrarVetted — already registered, rejected, or not yet vetted.
"Application is missing required registration data."Program, semester, batch, fee head, or campus wasn't set upstream.
"Regular students should be in Year One Semester One." (and similar)registrationTypeId doesn't match the applicant's semester.
"Please make sure that Admission Fee is Paid before proceeding."Outstanding admission fee ledger.
"Please make sure that Registration Fee is Paid before proceeding."Outstanding registration fee ledger — mirrors regPaid = false.
"Please make sure that Re-Registration Fee is Paid before proceeding."Existing-student registration type with an unpaid re-registration fee for that semester.
On success — the application flips to Registered server-side; remove it from the queue view (a fresh GET /applications or optimistic removal both work) and surface the returned credentials to the registrar.
GET /api/v1/admissions/registration-types GetRegistrationTypes

Lookup — the dropdown options for registrationTypeId. Fetchable on its own if needed; note this sits outside the registrar-desk group, at /api/v1/admissions/registration-types. No parameters.

"data": [
  { "intType": 1, "registrationTypeGuid": "a1...", "registrationType": "Regular" },
  { "intType": 2, "registrationTypeGuid": "b2...", "registrationType": "Lateral Entry" },
  { "intType": 3, "registrationTypeGuid": "c3...", "registrationType": "Credit Exemption" },
  { "intType": 4, "registrationTypeGuid": "d4...", "registrationType": "Existing Students" }
]
Submit intType as registrationTypeId on POST /register — the guid is for display/keying only, the command still takes the legacy int id.

Render as plain labels, not dropdowns. These are the record of a payment already made in Payment Console (semesterName, batchName, regPaymentTypeName, regReceiptBookCode) — the registrar isn't selecting them here.
